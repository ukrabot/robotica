Qué es ros2_control y por qué reemplazó a la arquitectura clásica de ROS 1

En la primera generación de ROS, el control de actuadores se realizaba a menudo mediante nodos ad-hoc que se suscribían a tópicos de mensajes estándar. Este enfoque sufría de graves problemas en brazos robóticos industriales: latencias no deterministas debidas a la serialización de middleware, riesgo de inversión de prioridades y falta de interfaces estandarizadas entre el hardware físico y los planificadores de movimiento como MoveIt.

El framework ros2_control es una completa reingeniería diseñada para cumplir los requisitos más estrictos de control en tiempo real determinista (Hard Real-Time) a frecuencias de 100 Hz a 1.000 Hz. Sus objetivos de diseño son:

  • Desacoplamiento total entre algoritmos y hardware: El mismo controlador de trayectoria funciona de forma idéntica en un simulador Gazebo, en un hardware real con servomotores EtherCAT o en un microcontrolador ESP32 mediante micro-ROS.
  • Gestión de ciclo de vida (Lifecycle Nodes): Controladores y componentes de hardware implementan estados de máquina estrictos (Unconfigured, Inactive, Active, Finalized) para evitar movimientos no deseados durante el arranque.
  • Acceso directo a memoria compartida sin copia (Zero-Copy): El Controller Manager intercambia comandos y estados mediante buffers de memoria directa sin serialización DDS en el bucle crítico.

Arquitectura interna: Resource Manager, Controllers e Interfaces

El sistema se organiza en cuatro capas claramente diferenciadas:

  1. Hardware Component (hardware_interface): Plugin dinámico en C++ que encapsula el protocolo de comunicación física (CANopen, EtherCAT, Modbus, Serial UART). Exporta State Interfaces (lecturas de posición, velocidad, esfuerzo) y Command Interfaces (consignas enviadas a los actuadores).
  2. Resource Manager: Administra el hardware registrado en el archivo URDF/xacro y garantiza que múltiples controladores no intenten escribir simultáneamente sobre la misma interfaz de comando.
  3. Controller Manager: El orquestador que ejecuta el bucle de control en tiempo real (llamando secuencialmente a read(), update() de controladores y write()).
  4. Controladores Activos (Controllers):
    • joint_state_broadcaster: Publica el estado articular en el tópico /joint_states para RViz y MoveIt.
    • joint_trajectory_controller: Recibe trayectorias complejas con curvas spline cúbicas/quínticas y calcula la interpolación en milisegundos.
    • forward_command_controller: Envía comandos directos de posición, velocidad o torque.

Desarrollo de un plugin HardwareInterface personalizado en C++

Para controlar un brazo robótico DIY o industrial, se debe heredar de la clase base hardware_interface::SystemInterface. A continuación se presenta la estructura mínima de un plugin funcional:

#include "hardware_interface/system_interface.hpp"
#include "hardware_interface/types/hardware_interface_type_values.hpp"
#include "rclcpp/rclcpp.hpp"

namespace mi_robot_hardware
{
class BrazoHardwareInterface : public hardware_interface::SystemInterface
{
public:
  CallbackReturn on_init(const hardware_interface::HardwareInfo & info) override
  {
    if (hardware_interface::SystemInterface::on_init(info) != CallbackReturn::SUCCESS) {
      return CallbackReturn::ERROR;
    }
    // Inicializar vectores de estado y comando para los 6 ejes
    hw_positions_.resize(info_.joints.size(), 0.0);
    hw_commands_.resize(info_.joints.size(), 0.0);
    return CallbackReturn::SUCCESS;
  }

  std::vector<hardware_interface::StateInterface> export_state_interfaces() override
  {
    std::vector<hardware_interface::StateInterface> state_interfaces;
    for (size_t i = 0; i < info_.joints.size(); ++i) {
      state_interfaces.emplace_back(hardware_interface::StateInterface(
        info_.joints[i].name, hardware_interface::HW_IF_POSITION, &hw_positions_[i]));
    }
    return state_interfaces;
  }

  std::vector<hardware_interface::CommandInterface> export_command_interfaces() override
  {
    std::vector<hardware_interface::CommandInterface> command_interfaces;
    for (size_t i = 0; i < info_.joints.size(); ++i) {
      command_interfaces.emplace_back(hardware_interface::CommandInterface(
        info_.joints[i].name, hardware_interface::HW_IF_POSITION, &hw_commands_[i]));
    }
    return command_interfaces;
  }

  hardware_interface::return_type read(const rclcpp::Time & time, const rclcpp::Duration & period) override
  {
    // Leer encoders vía bus CAN o puerto serie
    // driver_can_.leer_posiciones(hw_positions_);
    return hardware_interface::return_type::OK;
  }

  hardware_interface::return_type write(const rclcpp::Time & time, const rclcpp::Duration & period) override
  {
    // Enviar consignas de ángulo a los servodrives
    // driver_can_.enviar_comandos(hw_commands_);
    return hardware_interface::return_type::OK;
  }

private:
  std::vector<double> hw_positions_;
  std::vector<double> hw_commands_;
};
} // namespace mi_robot_hardware

#include "pluginlib/class_list_macros.hpp"
PLUGINLIB_EXPORT_CLASS(mi_robot_hardware::BrazoHardwareInterface, hardware_interface::SystemInterface)

Integración en URDF/xacro y archivo de controladores YAML

Para registrar el hardware en el árbol de descripción del robot, se añade la etiqueta <ros2_control> en el archivo URDF:

<ros2_control name="BrazoRobótico6Ejes" type="system">
  <hardware>
    <plugin>mi_robot_hardware/BrazoHardwareInterface</plugin>
    <param name="puerto_serie">/dev/ttyUSB0</param>
    <param name="baudrate">1000000</param>
  </hardware>
  <joint name="joint1">
    <command_interface name="position"/>
    <state_interface name="position"/>
    <state_interface name="velocity"/>
  </joint>
  <!-- Repetir para joint2 hasta joint6 -->
</ros2_control>

Archivo de configuración controllers.yaml:

controller_manager:
  ros__parameters:
    update_rate: 500  # 500 Hz (2 ms por ciclo)

    joint_state_broadcaster:
      type: joint_state_broadcaster/JointStateBroadcaster

    arm_controller:
      type: joint_trajectory_controller/JointTrajectoryController

arm_controller:
  ros__parameters:
    joints:
      - joint1
      - joint2
      - joint3
      - joint4
      - joint5
      - joint6
    command_interfaces:
      - position
    state_interfaces:
      - position
      - velocity
    open_loop_control: false
    allow_nonzero_velocity_at_trajectory_end: false
    constraints:
      stopped_velocity_tolerance: 0.01
      goal_time: 0.5

Kernel PREEMPT_RT y conexión con MoveIt 2

Para evitar fluctuaciones de latencia (Jitter) en frecuencias de 500 Hz o 1 kHz, el sistema operativo Ubuntu debe correr sobre un kernel con parche Linux PREEMPT_RT. Sin tiempo real, interrupciones de disco o procesos de fondo pueden demorar el hilo de control por más de 15 ms, provocando sacudidas mecánicas bruscas en el brazo robótico.

Para conectar MoveIt 2 con ros2_control, se utiliza el plugin moveit_simple_controller_manager configurado en moveit_controllers.yaml, el cual envía las trayectorias calculadas por el planificador cinemático directamente a la acción /arm_controller/follow_joint_trajectory.

Preguntas Frecuentes

¿Cuál es la diferencia entre SystemInterface y ActuatorInterface en ros2_control?

SystemInterface se utiliza para sistemas multieje acoplados (como un brazo robótico de 6 ejes completo) donde múltiples articulaciones se leen y escriben a través de un único bus de comunicación. ActuatorInterface se usa para un motor modular individual independiente (por ejemplo, una rueda de tracción o una pinza monocanal).

¿Puedo usar ros2_control con microcontroladores Arduino o ESP32?

Sí, a través de dos métodos: implementando un protocolo de comunicación serie binario rápido en C++ dentro de tu HardwareInterface personalizado, o utilizando micro-ROS ejecutándose en el ESP32 para exportar directamente las interfaces de hardware a través de la red WiFi o USB.

¿Por qué el comando ros2 control list_hardware_interfaces muestra interfaces no disponibles?

Generalmente ocurre porque el componente de hardware no ha sido activado por el Controller Manager o falló durante el método `on_activate()`. Verifica que el nodo `ros2_control_node` esté ejecutándose y que no existan errores de comunicación en el log de la terminal.

¿Qué función cumple joint_state_broadcaster?

Es un controlador de lectura pasiva que toma las `state_interfaces` (posición, velocidad y esfuerzo) de todos los actuadores registrados y las publica periódicamente como un mensaje `sensor_msgs/msg/JointState` en el tópico `/joint_states`, permitiendo que `robot_state_publisher` calcule las transformaciones TF3D del robot.

¿Cómo simular mi brazo en Gazebo usando ros2_control?

Solo necesitas sustituir el tag `` de tu hardware real por el plugin oficial `gz_ros2_control/GazeboSimSystem` en el URDF. De este modo, los mismos controladores de trayectoria funcionarán en el simulador sin cambiar ni una sola línea de código de tu aplicación.
