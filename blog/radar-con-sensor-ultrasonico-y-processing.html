El principio físico: tiempo de vuelo del ultrasonido

El sensor HC-SR04 mide distancia usando el mismo principio físico que emplean los murciélagos para orientarse en la oscuridad: emite un pulso de sonido en una frecuencia por encima del rango audible humano (40 kHz, de ahí el término ultrasonido), y mide cuánto tiempo tarda ese pulso en rebotar contra un objeto y regresar como eco a un receptor.

Físicamente, el sensor tiene dos elementos visibles como pequeños "ojos" cilíndricos: uno actúa como emisor (Trig) y el otro como receptor (Echo). El proceso de medición sigue una secuencia precisa:

  1. Arduino envía un pulso HIGH de 10 microsegundos al pin Trig, indicándole al sensor que emita el pulso ultrasónico.
  2. El sensor emite una ráfaga de 8 pulsos a 40 kHz por su emisor.
  3. El pin Echo se pone en HIGH exactamente en el instante en que se emite el sonido, y permanece en HIGH hasta que el eco de regreso es detectado por el receptor.
  4. Arduino mide, con la función pulseIn(), cuánto tiempo exacto permaneció el pin Echo en HIGH — ese tiempo es directamente proporcional a la distancia recorrida por el sonido, ida y vuelta.

Conociendo la velocidad del sonido en el aire (aproximadamente 343 metros por segundo a 20°C, o 0.0343 cm por microsegundo), y sabiendo que el sonido recorre la distancia dos veces (ida hacia el objeto, vuelta hacia el sensor), la fórmula para calcular la distancia es:

distancia_cm = (tiempo_microsegundos * 0.0343) / 2
Por qué se divide entre 2: el tiempo medido por pulseIn() corresponde al viaje completo de ida y vuelta del sonido, no solo a la distancia hacia el objeto. Dividir entre 2 corrige esto para obtener la distancia real entre el sensor y el objeto detectado.

Arquitectura del proyecto: Arduino mide, Processing dibuja

Este proyecto combina dos piezas de software con responsabilidades claramente separadas, un patrón de diseño muy común en proyectos de visualización de datos de sensores:

  • Arduino se encarga exclusivamente de la parte física: mueve el servomotor a través de un rango de ángulos (típicamente de 15° a 165°), toma una medición de distancia en cada ángulo con el HC-SR04, y envía ambos valores —ángulo y distancia— por el puerto serie hacia el computador, en un formato de texto simple y predecible.
  • Processing, ejecutándose en el computador, escucha ese mismo puerto serie, interpreta el texto recibido, y usa esos dos valores (ángulo y distancia) para calcular la posición exacta donde dibujar un punto en la pantalla, generando en tiempo real la clásica animación de "barrido de radar" con el efecto de estela verde tan reconocible del cine y los sistemas de navegación reales.

Esta separación es deliberada: Arduino es excelente controlando hardware físico en tiempo real con precisión de microsegundos, pero no tiene absolutamente ninguna capacidad de dibujar gráficos en una pantalla. Processing, por su parte, está construido específicamente para gráficos y visualización, pero no puede leer directamente un sensor ultrasónico conectado por cable a pines físicos. Combinarlos aprovecha lo mejor de cada herramienta.

Conexión de hardware: sensor sobre servomotor

El montaje físico consiste en fijar el sensor HC-SR04 sobre el brazo (horn) del servomotor, de modo que al girar el servo, el sensor "apunte" hacia distintos ángulos, barriendo el área frente a él como si fuera la antena giratoria de un radar real.

Esquema conceptual de conexión:

HC-SR04 VCC  ----> Arduino 5V
HC-SR04 GND  ----> Arduino GND
HC-SR04 Trig ----> Arduino pin digital 9
HC-SR04 Echo ----> Arduino pin digital 10

Servo SG90 (cable rojo, señal naranja/amarilla, cable marron/negro):
Rojo    ----> Arduino 5V
Marron  ----> Arduino GND
Naranja ----> Arduino pin digital 11
Sobre la alimentación del servo: un servomotor SG90 puede consumir picos de corriente notablemente superiores a los que el pin 5V de Arduino puede entregar de forma sostenida y segura, especialmente si el sensor y otros componentes comparten la misma alimentación. Para pruebas cortas de este proyecto suele funcionar sin problema alimentando todo desde el mismo Arduino, pero si notas reinicios inesperados de la placa o movimientos erráticos del servo, considera alimentar el servomotor desde una fuente externa de 5V independiente, compartiendo únicamente la tierra (GND) con Arduino.

El montaje mecánico —fijar físicamente el sensor al brazo del servo— es la parte más artesanal del proyecto. Una solución simple y muy usada en la comunidad es recortar una pequeña pieza de cartón rígido o plástico en forma de "L", pegarla al brazo del servo por un lado, y al cuerpo del sensor por el otro, asegurando que quede centrado y estable durante el giro.

Código Arduino: barrido y medición de distancia

El siguiente código controla el barrido del servomotor de un extremo a otro y, en cada ángulo, toma una medición de distancia con el HC-SR04, enviando ambos valores por el puerto serie en un formato de texto simple que Processing podrá interpretar fácilmente.

#include <Servo.h>

const int PIN_TRIG = 9;
const int PIN_ECHO = 10;
const int PIN_SERVO = 11;

Servo servoRadar;

void setup() {
  pinMode(PIN_TRIG, OUTPUT);
  pinMode(PIN_ECHO, INPUT);
  servoRadar.attach(PIN_SERVO);
  Serial.begin(9600);
}

long medirDistanciaCm() {
  digitalWrite(PIN_TRIG, LOW);
  delayMicroseconds(2);
  digitalWrite(PIN_TRIG, HIGH);
  delayMicroseconds(10);
  digitalWrite(PIN_TRIG, LOW);

  long tiempoEcoMicrosegundos = pulseIn(PIN_ECHO, HIGH, 30000);
  if (tiempoEcoMicrosegundos == 0) return 400; // sin eco: asumir distancia maxima

  long distancia = (tiempoEcoMicrosegundos * 0.0343) / 2;
  return constrain(distancia, 2, 400);
}

void loop() {
  // Barrido de 15 a 165 grados
  for (int angulo = 15; angulo <= 165; angulo++) {
    servoRadar.write(angulo);
    delay(15); // tiempo para que el servo llegue fisicamente al angulo
    long distancia = medirDistanciaCm();

    Serial.print(angulo);
    Serial.print(",");
    Serial.print(distancia);
    Serial.print(".");
  }

  // Barrido de regreso, de 165 a 15 grados
  for (int angulo = 165; angulo >= 15; angulo--) {
    servoRadar.write(angulo);
    delay(15);
    long distancia = medirDistanciaCm();

    Serial.print(angulo);
    Serial.print(",");
    Serial.print(distancia);
    Serial.print(".");
  }
}

El formato de datos enviado es deliberadamente simple: cada medición se envía como angulo,distancia. — con una coma separando ángulo de distancia, y un punto marcando el final de cada lectura completa. Este formato, aunque minimalista, es exactamente lo que el código de Processing espera recibir, y es un patrón de comunicación serie muy común: texto plano con delimitadores simples, fácil de generar en Arduino y fácil de interpretar (parsear) en el lado receptor.

Instalar Processing y librerías necesarias

Processing es un entorno de programación gratuito y de código abierto, disponible para Windows, macOS y Linux desde el sitio oficial processing.org. A diferencia del IDE de Arduino, Processing no requiere instalación tradicional en la mayoría de los sistemas: se descarga como un archivo comprimido, se descomprime, y se ejecuta directamente.

  1. Descarga la versión correspondiente a tu sistema operativo desde el sitio oficial de Processing.
  2. Descomprime el archivo descargado en una carpeta de tu elección.
  3. Ejecuta el archivo Processing (o Processing.exe en Windows) para abrir el entorno.
  4. Verifica que la librería Serial esté disponible: en versiones recientes de Processing viene incluida por defecto como parte del núcleo del lenguaje (processing.serial.*), sin necesidad de instalación adicional.
Un desafío común de conexión: Arduino y Processing no pueden usar el puerto serie al mismo tiempo. Si tienes el Monitor Serie del IDE de Arduino abierto mientras intentas ejecutar el sketch de Processing, obtendrás un error de puerto ocupado. Asegúrate de cerrar el Monitor Serie de Arduino antes de ejecutar el código de Processing.

Código Processing: dibujando el radar

El siguiente sketch de Processing recibe los datos enviados por Arduino, los interpreta, y dibuja la interfaz visual de radar: un fondo con líneas de referencia angular, un "brazo" de barrido animado que gira en sincronía con el servomotor real, y puntos que representan los objetos detectados en cada ángulo.

import processing.serial.*;

Serial puertoSerial;
String datosEntrantes = "";
int anguloActual = 0;
int distanciaActual = 0;

void setup() {
  size(1200, 700);

  // IMPORTANTE: ajustar el indice segun tu propio puerto serie
  // Ejecutar primero: println(Serial.list()); para ver los puertos disponibles
  String nombrePuerto = Serial.list()[0];
  puertoSerial = new Serial(this, nombrePuerto, 9600);
  puertoSerial.bufferUntil('.');
}

void draw() {
  fondoRadar();
  dibujarLineasAngulares();
  dibujarBrazoBarrido();
  dibujarTextoDistancia();
}

void serialEvent(Serial puerto) {
  datosEntrantes = puerto.readStringUntil('.');
  datosEntrantes = datosEntrantes.substring(0, datosEntrantes.length() - 0);

  if (datosEntrantes != null) {
    datosEntrantes = trim(datosEntrantes);
    int indiceComa = datosEntrantes.indexOf(",");
    if (indiceComa > 0) {
      String parteAngulo = datosEntrantes.substring(0, indiceComa);
      String parteDistancia = datosEntrantes.substring(indiceComa + 1, datosEntrantes.length());
      anguloActual = int(parteAngulo);
      distanciaActual = int(parteDistancia);
    }
  }
}

void fondoRadar() {
  background(0, 20, 0);
  noStroke();
  fill(0, 40, 0, 60);
  rect(0, height / 2, width, height / 2);
}

void dibujarLineasAngulares() {
  pushMatrix();
  translate(width / 2, height - 50);
  stroke(0, 255, 0);
  noFill();

  // Arcos concentricos de distancia (cada 100px = referencia de distancia)
  for (int r = 100; r <= 500; r += 100) {
    arc(0, 0, r * 2, r * 2, PI, TWO_PI);
  }

  // Lineas radiales cada 30 grados
  for (int a = 0; a <= 180; a += 30) {
    float x = 500 * cos(radians(180 - a));
    float y = -500 * sin(radians(180 - a));
    line(0, 0, x, y);
  }
  popMatrix();
}

void dibujarBrazoBarrido() {
  pushMatrix();
  translate(width / 2, height - 50);

  stroke(0, 255, 0);
  strokeWeight(3);
  float x = 500 * cos(radians(180 - anguloActual));
  float y = -500 * sin(radians(180 - anguloActual));
  line(0, 0, x, y);

  // Punto del objeto detectado, si esta dentro de un rango razonable
  if (distanciaActual < 400) {
    float escala = map(distanciaActual, 0, 400, 0, 500);
    float px = escala * cos(radians(180 - anguloActual));
    float py = -escala * sin(radians(180 - anguloActual));
    noStroke();
    fill(255, 0, 0);
    ellipse(px, py, 12, 12);
  }
  popMatrix();
}

void dibujarTextoDistancia() {
  fill(0, 255, 0);
  textSize(20);
  text("Angulo: " + anguloActual + " grados", 20, 30);
  text("Distancia: " + distanciaActual + " cm", 20, 60);
}

La función serialEvent() es el corazón de la comunicación: se ejecuta automáticamente cada vez que Processing recibe un mensaje completo terminado en el carácter . (configurado con bufferUntil('.') en setup()), separa el texto recibido en la parte del ángulo y la parte de la distancia usando la posición de la coma, y actualiza las variables globales que el resto del sketch usa para dibujar.

De coordenadas polares a cartesianas: la matemática del radar

El dato que Arduino envía —un ángulo y una distancia— es lo que en matemáticas se conoce como coordenadas polares: una forma de ubicar un punto en el espacio a partir de una dirección (el ángulo) y una magnitud (la distancia desde un origen), en vez de usar las coordenadas horizontal/vertical (x, y) habituales de una pantalla.

Processing, como la mayoría de entornos gráficos, dibuja usando coordenadas cartesianas (x, y), por lo que es necesario convertir de un sistema a otro antes de poder ubicar el punto correctamente en pantalla. La conversión se basa en trigonometría básica:

x = distancia * cos(angulo)
y = distancia * sin(angulo)

En el código de Processing de esta guía, esta conversión ocurre exactamente en las líneas que calculan px y py dentro de dibujarBrazoBarrido(), usando las funciones trigonométricas nativas cos() y sin() de Processing (que trabajan en radianes, de ahí la conversión con radians()). El ajuste 180 - angulo y el signo negativo en la coordenada y son correcciones necesarias porque el sistema de coordenadas de pantalla de Processing tiene el eje Y invertido respecto a la convención matemática estándar (en pantalla, "hacia abajo" es positivo), y porque el barrido del servo va de izquierda a derecha en vez de seguir la convención matemática de ángulos crecientes en sentido antihorario.

Por qué entender esto importa más allá de este proyecto: la conversión de coordenadas polares a cartesianas es una herramienta matemática que reaparece constantemente en robótica, gráficos por computador y procesamiento de señales — desde calcular la posición de las patas de un robot hexápodo hasta dibujar un reloj analógico digital. Dominarla en el contexto simple de este radar es una base sólida para proyectos mucho más ambiciosos.

Calibración y ajuste de precisión

  1. Identifica el puerto serie correcto: antes de ejecutar el sketch completo de Processing, ejecuta temporalmente solo la línea println(Serial.list()) dentro de setup() para ver la lista de puertos disponibles en la consola, e identifica el índice correspondiente a tu Arduino, ajustando el índice [0] del código si es necesario.
  2. Ajusta el delay del servo: el valor de delay(15) tras cada movimiento del servo en el código Arduino es un balance entre velocidad de barrido y precisión angular — un valor muy bajo hace que el servo dispare la medición antes de llegar físicamente al ángulo solicitado, generando datos inconsistentes.
  3. Considera la temperatura ambiente: la velocidad del sonido usada en el cálculo (0.0343 cm/microsegundo) corresponde a aproximadamente 20°C. En ambientes muy fríos o muy calurosos, esta constante introduce un pequeño error sistemático que, para la mayoría de los usos de hobby, es despreciable pero vale la pena conocer.
  4. Verifica el rango de distancia máxima mostrado: el mapeo map(distanciaActual, 0, 400, 0, 500) en Processing asume un rango máximo de 400 cm; si tu espacio de pruebas es mucho más pequeño, reducir este valor máximo hace que el radar aproveche mejor el espacio visual disponible en pantalla.
  5. Prueba con distintas superficies: materiales blandos, angulados o muy pequeños reflejan menos sonido de vuelta al sensor y pueden generar lecturas erráticas o de distancia máxima aunque haya un objeto presente — es una limitación física real del ultrasonido, no un error de programación.

Mejoras posibles y siguientes pasos

  • Efecto de estela (fade trail): en vez de borrar completamente el fondo en cada frame, dibujar un rectángulo semitransparente sobre el frame anterior crea el efecto de "desvanecimiento" verde tan característico de los radares de películas, donde los puntos detectados se desvanecen gradualmente en vez de desaparecer instantáneamente.
  • Alarma sonora de proximidad: hacer que Processing reproduzca un sonido de "beep" cuando se detecta un objeto por debajo de una distancia crítica, útil como sistema de alerta simple.
  • Registro de detecciones con marca de tiempo: guardar en un archivo cada detección significativa (ángulo, distancia, momento) para análisis posterior de patrones de movimiento en el área monitoreada.
  • Migrar a un sensor láser ToF (Time of Flight): sensores como el VL53L0X ofrecen mayor precisión y velocidad de medición que el ultrasonido, a cambio de mayor costo y un protocolo de comunicación I2C en vez de la simple lectura de pulso del HC-SR04.
  • Radar de 360 grados: reemplazar el servomotor de barrido limitado (0-180°) por un motor de rotación continua o un sistema de deslizamiento (slip ring), permitiendo un giro completo sin las limitaciones mecánicas de un servo estándar.

Conclusión

El radar con HC-SR04 y Processing es uno de esos proyectos donde el resultado visual final —una animación de radar en tiempo real, sincronizada con un servomotor físico girando frente a ti— genera una sensación de logro desproporcionadamente grande respecto a la complejidad real de construirlo. En el camino se aprenden conceptos que trascienden ampliamente este proyecto puntual: el principio físico del tiempo de vuelo de una onda, la separación de responsabilidades entre hardware de medición y software de visualización, un protocolo simple de comunicación serie con delimitadores de texto, y la conversión de coordenadas polares a cartesianas mediante trigonometría básica. Estas herramientas conceptuales reaparecerán, en formas distintas, en prácticamente cualquier proyecto futuro que combine sensores físicos con visualización de datos en pantalla.

Preguntas frecuentes

¿Qué es Processing y por qué se usa junto con Arduino en este proyecto?

Processing es un lenguaje y entorno de programación de código abierto orientado a las artes visuales y la visualización de datos, basado en Java, con una curva de aprendizaje muy suave. Se usa junto con Arduino en este proyecto porque Arduino no tiene capacidad nativa de dibujar gráficos: su rol es medir distancias y controlar el servomotor, mientras que Processing recibe esos datos por el puerto serie y los transforma en la representación visual del radar en la pantalla del computador. Esta división de responsabilidades (Arduino mide, Processing dibuja) es un patrón extremadamente común en proyectos de visualización de datos de sensores.

¿Qué tan preciso es el sensor ultrasónico HC-SR04?

El HC-SR04 tiene una precisión típica de ±0.3 cm en condiciones ideales, con un rango de medición efectivo de aproximadamente 2 cm a 400 cm. Su precisión se degrada notablemente con superficies que absorben o desvían el sonido, como telas, espuma o superficies muy anguladas respecto al sensor, así como con cambios significativos de temperatura ambiente, ya que la velocidad del sonido en el aire varía con la temperatura. Para un proyecto de radar de hobby, esta precisión es más que suficiente; para aplicaciones que requieran exactitud milimétrica se necesitarían sensores láser tipo ToF (Time of Flight).

¿Por qué el radar en Processing se ve entrecortado o con movimiento poco fluido?

La causa más común es un delay demasiado largo en el código Arduino entre cada movimiento del servo y cada lectura del sensor, sumado a la limitación física del propio HC-SR04, que necesita un tiempo mínimo de silencio entre mediciones consecutivas para evitar ecos residuales de la medición anterior. Reducir el delay del servo demasiado agresivamente introduce otro problema: el servomotor físicamente no alcanza a llegar a la posición angular solicitada antes de que se dispare la siguiente medición, generando lecturas asociadas a ángulos incorrectos. Encontrar el balance entre velocidad de barrido y precisión angular es parte del proceso de calibración de este proyecto.

¿Puedo usar este mismo proyecto para detectar más de un objeto a la vez?

El HC-SR04 solo entrega la distancia al objeto más cercano dentro de su cono de detección en cada medición individual, por lo que no puede distinguir directamente múltiples objetos en un mismo ángulo. Sin embargo, sí es posible detectar múltiples objetos ubicados en ángulos distintos durante el barrido completo del servomotor, ya que cada ángulo genera su propia lectura independiente. El código de Processing de esta guía ya soporta esto de forma natural: cada punto detectado en cualquier ángulo del barrido se dibuja en el radar, permitiendo visualizar varios objetos distribuidos en diferentes direcciones alrededor del sensor.

¿Qué diferencia hay entre este radar y uno real usado en aviación o navegación marítima?

Un radar real emite ondas electromagnéticas (radio) y mide el tiempo que tardan en rebotar en un objeto y regresar, lo que le permite detectar objetos a kilómetros de distancia, incluso a través de condiciones climáticas adversas. Este proyecto usa ultrasonido (ondas de sonido) en vez de ondas de radio, con un alcance de centímetros en vez de kilómetros, y depende de una barrida mecánica lenta con servomotor en vez de una antena giratoria de alta velocidad o un arreglo de antenas electrónico. El principio físico de fondo —medir tiempo de vuelo de una onda reflejada para calcular distancia— es el mismo, lo que hace de este proyecto una introducción conceptualmente honesta al funcionamiento de un radar real, aunque a una escala y con una tecnología completamente distintas.
