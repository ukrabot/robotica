Docker en Raspberry Pi: Contenedores para Proyectos Caseros

Contener servicios facilita instalarlos y recuperarlos, pero no reemplaza respaldos, actualizaciones ni una buena arquitectura de almacenamiento.

Cuándo Docker aporta valor en una Raspberry Pi

Docker empaqueta aplicación y dependencias en una imagen reproducible. Es ideal para Home Assistant complementario, MQTT, Grafana, Node-RED, DNS local o un panel de sensores: cada servicio mantiene sus bibliotecas y puede actualizarse o revertirse sin contaminar el sistema base.

No convierte una Pi en un hipervisor ni elimina límites de RAM y E/S. Para controlar GPIO con latencia estricta, tareas de arranque temprano o hardware que necesita módulos del kernel, un servicio systemd nativo puede ser más simple y predecible.

Sistema, arquitectura y almacenamiento

Usa Raspberry Pi OS de 64 bits en Pi 3, 4 o 5 para acceder al ecosistema arm64. Actualiza firmware y paquetes antes de instalar desde el repositorio oficial de Docker. Verifica que cada imagen publique variante ARM64; una etiqueta que solo contiene amd64 fallará o recurrirá a emulación lenta.

Para servicios con escrituras constantes, conecta un SSD USB 3 o NVMe. Las tarjetas microSD sufren con bases de datos y logs. Mantén el sistema y los datos importantes en almacenamiento fiable, con alimentación estable.

Un proyecto reproducible con Compose

Este ejemplo crea un broker MQTT y Node-RED en una red interna, publica solo los puertos necesarios y conserva datos en directorios visibles:

services:
  mqtt:
    image: eclipse-mosquitto:2
    restart: unless-stopped
    ports: ["1883:1883"]
    volumes:
      - ./mosquitto/config:/mosquitto/config:ro
      - ./mosquitto/data:/mosquitto/data
  nodered:
    image: nodered/node-red:latest
    restart: unless-stopped
    ports: ["1880:1880"]
    volumes:
      - ./nodered:/data
    depends_on: [mqtt]
networks:
  default:
    name: automatizacion

Valida con docker compose config y arranca con docker compose up -d. Fija versiones en producción en lugar de depender de latest, porque una actualización mayor puede romper datos o configuración.

Volúmenes, permisos y respaldo

Los bind mounts facilitan inspección y respaldo; los volúmenes administrados reducen errores de rutas. En ambos casos, averigua con qué UID/GID corre el contenedor y asigna permisos mínimos. No soluciones todo con chmod 777.

Un respaldo consistente requiere detener el servicio o usar el mecanismo de exportación de la base de datos. Copiar archivos de SQLite o una base activa puede crear una copia incoherente. Conserva también compose.yaml, archivos .env sin secretos en Git y una lista de versiones.

Redes y acceso desde casa

Por defecto, Compose crea una red y los servicios se encuentran por nombre. Publica al host solo lo que usarán otros dispositivos. No expongas bases de datos ni el socket Docker. Para acceso remoto, prefiere VPN como WireGuard/Tailscale o un proxy inverso con TLS y autenticación.

El grupo docker equivale prácticamente a root. Un usuario capaz de montar el sistema host dentro de un contenedor puede controlar la Raspberry Pi. Añade solo administradores de confianza.

Límites, salud y observabilidad

Una Pi de 2 GB puede quedarse sin memoria con varias bases y paneles. Observa docker stats, temperatura y espacio. Configura rotación de logs; un contenedor verboso puede llenar el disco aunque sus datos sean pequeños.

Define healthchecks cuando la imagen los soporte. “Contenedor en ejecución” no significa “servicio responde correctamente”.

Actualización y recuperación sin sorpresas

  1. Lee notas de versión y haz respaldo verificable.
  2. Descarga la versión fijada con docker compose pull.
  3. Recrea con docker compose up -d.
  4. Revisa salud y logs.
  5. Conserva temporalmente la imagen anterior para retroceder.

Documenta desde una instalación vacía. Si puedes restaurar compose.yaml, secretos y datos en otra tarjeta o Pi, el proyecto es realmente reproducible.

Caso práctico: recuperar la automatización en una Raspberry Pi nueva

Un sistema doméstico ejecuta MQTT, Node-RED y una base de series temporales. La microSD falla. En vez de reconstruir manualmente, se instala Raspberry Pi OS de 64 bits, Docker desde el repositorio oficial y se restaura un directorio que contiene Compose, configuraciones y backup consistente de datos. Los secretos se recuperan desde el gestor separado.

Tras docker compose up -d, los healthchecks confirman servicios, pero Node-RED no accede a un dispositivo USB porque cambió la ruta. Se corrige mediante una regla udev estable, no codificando /dev/ttyUSB0. El ejercicio tarda 40 minutos y revela la única dependencia no documentada.

Checklist operativo mensual

  • Revisar imágenes con actualizaciones de seguridad y notas de versión.
  • Comprobar espacio, logs, temperatura y eventos OOM.
  • Restaurar un flujo o base en un entorno temporal.
  • Exportar Compose resuelto y registrar versiones/digests.

Conclusión y criterio de compra o implementación

La decisión correcta no es la que maximiza una cifra de catálogo, sino la que controla los riesgos y puede verificarse. Define primero el caso de uso, mide el sistema completo y conserva margen térmico, eléctrico y operativo. Documentar la configuración y repetir una prueba breve antes de confiarle un trabajo crítico evita más problemas que cualquier accesorio.

Preguntas frecuentes

¿Docker funciona en Raspberry Pi Zero?

En Zero 2 W puede funcionar con imágenes ARM64 ligeras, pero RAM y almacenamiento limitan mucho. La Zero original ARMv6 tiene compatibilidad menor.

¿Conviene Docker o instalar paquetes directamente?

Docker conviene con varios servicios y necesidad de reproducibilidad. Para una única tarea ligada al hardware, systemd puede ser más simple.

¿Puedo usar tarjeta microSD?

Sí para cargas ligeras, pero bases de datos y logs reducen su vida. Un SSD y respaldos son mejores para operación continua.

¿Es seguro abrir los puertos a Internet?

No directamente. Usa VPN o proxy TLS con autenticación, actualiza imágenes y publica solo los puertos imprescindibles.
