ESP32 con Bluetooth BLE: Control desde el Celular

BLE no es un puerto serie invisible: es un pequeño esquema de servicios y permisos. Entender GATT una vez desbloquea el control del ESP32 desde cualquier celular, Android o iPhone.

BLE, Bluetooth clásico o Wi-Fi: cuál usar

El ESP32 trae radio 2,4 GHz compartida entre Wi-Fi y Bluetooth, con dos perfiles muy distintos. El Bluetooth clásico (SPP) mueve datos como un puerto serie invisible: simple y rápido, pero solo con Android (iOS nunca lo soportó). El BLE es el estándar de los dispositivos de batería: relojes, sensores y bombillas. Wi-Fi ofrece throughput y acceso remoto a cambio de consumo.

CriterioBLEBT clásico (SPP)Wi-Fi
iOSSíNoSí
ConsumoMuy bajoMedioAlto
Throughput útil~10–50 KB/s~100–200 KB/sMB/s
Acceso desde fuera de casaNoNoSí
Ideal paraControl y telemetría de un dispositivoTerminal serie AndroidCámara, MQTT, domótica

Para “controlar algo desde el celular a pocos metros” la respuesta casi siempre es BLE, y esta guía se concentra en él.

GATT explicado en cinco minutos

BLE organiza los datos en GATT: un servidor (el ESP32) expone servicios que contienen características, y cada característica tiene permisos:

PropiedadQué haceEjemplo
READEl celular lee el valor actualEstado de un LED
WRITEEl celular escribe un comandoEncender/apagar
NOTIFYEl servidor empuja datos sin confirmaciónTemperatura cada 5 s
INDICATEComo NOTIFY con acuse de reciboAlarmas críticas

Cada servicio y característica se identifica por un UUID: puedes usar uno oficial (por ejemplo el de batería 0x180F) o generar uno de 128 bits propio para tu proyecto. Con una app genérica verás el árbol completo y podrás leer, escribir y suscribirte a notify sin escribir una línea de código móvil.

Bluedroid o NimBLE: elegir la pila

El ESP32 ofrece dos pilas BLE en ESP-IDF (y por extensión en Arduino): Bluedroid, la histórica, muy completa y hambrienta de RAM; y NimBLE, moderna y compacta. Con Bluedroid, un proyecto con Wi-Fi + BLE puede quedarse sin heap; NimBLE libera decenas de KB.

CriterioBluedroidNimBLE
RAM reservadaAlta (~50 KB+ del heap)Baja (mucho menor)
API Arduino clásica (BLEDevice.h)NativaVía librería NimBLE-Arduino
CompatibilidadMáxima, tutoriales abundantesExcelente y creciente
Recomendada si…Seguimos un tutorial antiguoEl heap es escaso o el proyecto es serio

Para empezar, la librería BLE del core Arduino (Bluedroid) funciona sin instalaciones extra; cuando el proyecto crezca, migra a NimBLE-Arduino manteniendo la lógica.

Firmware completo en Arduino

Este sketch expone un servicio con dos características: un LED que se controla por WRITE y un contador que se notifica cada segundo. Compila con el core arduino-esp32 (placa “ESP32 Dev Module”):

#include <BLEDevice.h>
#include <BLEServer.h>
#include <BLEUtils.h>
#include <BLE2902.h>

#define SERVICE_UUID        "4fafc201-1fb5-459e-8fcc-c5c9c331914b"
#define CHAR_LED_UUID       "beb5483e-36e1-4688-b7f5-ea07361b26a8"
#define CHAR_CONTADOR_UUID  "1c95d5e3-d8f7-4feb-a774-4362d725d1b7"

BLECharacteristic* pContador;
bool dispositivoConectado = false;
uint32_t contador = 0;

class CallbacksLed : public BLECharacteristicCallbacks {
  void onWrite(BLECharacteristic* pChar) override {
    String valor = pChar->getValue();       // "1" enciende, "0" apaga
    if (valor.length() > 0) digitalWrite(2, valor[0] == '1' ? HIGH : LOW);
  }
};

class CallbacksServer : public BLEServerCallbacks {
  void onConnect(BLEServer* pServer) override { dispositivoConectado = true; }
  void onDisconnect(BLEServer* pServer) override {
    dispositivoConectado = false;
    pServer->getAdvertising()->start();      // vuelve a anunciar
  }
};

void setup() {
  pinMode(2, OUTPUT);
  BLEDevice::init("ESP32-Taller");
  BLEServer* pServer = BLEDevice::createServer();
  pServer->setCallbacks(new CallbacksServer());

  BLEService* pService = pServer->createService(SERVICE_UUID);

  BLECharacteristic* pLed = pService->createCharacteristic(
      CHAR_LED_UUID, BLECharacteristic::PROPERTY_WRITE);
  pLed->setCallbacks(new CallbacksLed());

  pContador = pService->createCharacteristic(
      CHAR_CONTADOR_UUID,
      BLECharacteristic::PROPERTY_READ | BLECharacteristic::PROPERTY_NOTIFY);
  pContador->addDescriptor(new BLE2902());

  pService->start();
  pServer->getAdvertising()->addServiceUUID(SERVICE_UUID);
  pServer->getAdvertising()->start();
}

void loop() {
  if (dispositivoConectado) {
    contador++;
    pContador->setValue(contador);
    pContador->notify();                    // empuja el valor al celular
  }
  delay(1000);
}

Tres detalles que ahorran horas: el BLE2902 es el descriptor CCCD que hace funcionar notify; sin reiniciar el advertising en onDisconnect el celular no vuelve a encontrar el dispositivo; y el nombre del anuncio conviene cambiarlo por uno reconocible.

Control desde el celular

Con nRF Connect (Android/iOS) o LightBlue el flujo es siempre el mismo:

  1. Escanea y conéctate a “ESP32-Taller”.
  2. Abre el servicio 4fafc201… y verás las dos características.
  3. Escribe 31 (hexadecimal de “1”) en la característica del LED: el LED azul del ESP32 enciende.
  4. Suscríbete (icono de flechas triple) a la característica del contador y observa los valores llegando cada segundo.

Para una app propia tienes tres rutas: MIT App Inventor con su componente BluetoothLE (arranque en una tarde), Flutter con flutter_blue_plus para algo serio multiplataforma, o Web Bluetooth desde Chrome/Edge de escritorio y Android, que no requiere instalar nada pero no funciona en iOS Safari.

Consumo, intervalos y alcance real

El consumo BLE depende del connection interval: el par negocia cada cuánto conversa (7,5 ms a 4 s). Intervalos largos (1–2 s) con notify esporádicos mantienen el ESP32 en decenas de miliamperios; intervalos cortos para respuesta tipo joystick suben el consumo pero siguen muy por debajo de Wi-Fi.

El MTU por defecto limita cada paquete a ~20 bytes útiles; solicita MTU 512 desde la app para telemetría densa. El alcance indoor real con la antena PCB del módulo: 10–20 m y un muro húmedo; no creas los “100 m de línea de vista” en departamentos con muros de hormigón.

Si el proyecto vive a pilas, la combinación ganadora es NimBLE + intervalo largo + GPIO deep sleep entre notificaciones, no solo cambiar de pila.

Diez errores típicos y su solución

  1. No aparece el dispositivo en el escáner: el advertising se detuvo tras una desconexión; reinícialo en onDisconnect.
  2. Heap agotado al iniciar BLE: usa NimBLE o reduce buffers de Bluedroid.
  3. Notify no llega: falta el descriptor CCCD (BLE2902) o el celular no se suscriyó.
  4. Se desconecta a los ~30 s: el supervisor de conexión expira; mantén tráfico o alarga el intervalo con la API de conexión.
  5. Escritura que no hace nada: la app escribe en hexadecimal; “1” debe enviarse como 0x31 o usa texto UTF-8 según la app.
  6. iOS no reconecta: usa bonding o reinicia el advertising tras cada desconexión.
  7. BLE y Wi-Fi juntos caen el rendimiento: comparten antena; espera throughput reducido y evita Wi-Fi de canal 1.
  8. Nombre truncado en el anuncio: el paquete de advertising cabe 31 bytes; usa el scan response para el nombre completo.
  9. Funciona con Android y no con iPhone: revisa permisos de Bluetooth (iOS 13+) y que el UUID sea 128 bits válido.
  10. Batería se agota en días: mide con amperímetro el sueño real; un LED de encendido puede consumir más que la radio.

Preguntas frecuentes

¿Puedo enviar audio por BLE con el ESP32?

No de forma práctica: el audio A2DP vive en Bluetooth clásico. Para audio usa SPP clásico o Wi-Fi, o un chip dedicado.

¿Por qué mi celular no encuentra el ESP32?

Casi siempre el advertising se detuvo tras una desconexión. Reinicia el advertising en el callback onDisconnect y verifica que el nombre no exceda el paquete.

¿BLE y Wi-Fi funcionan a la vez?

Sí, comparten la misma radio y antena con tiempo compartido: el throughput de ambos baja. Es usable para control, no para streaming.

¿Cuánta RAM consume la pila BLE?

Bluedroid reserva del orden de 50 KB o más del heap; NimBLE necesita bastante menos y es la opción cuando el proyecto también usa Wi-Fi.
