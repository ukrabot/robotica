FreeRTOS en ESP32: Multitarea Real en Microcontroladores

El ESP32 ya ejecuta FreeRTOS aunque nunca lo hayas llamado: tu loop() es una tarea más compitiendo con otras decenas. Tomar el control del planificador —tareas, prioridades, colas— es lo que separa un proyecto que funciona en el banco de uno que funciona instalado.

Por qué tu loop() ya es FreeRTOS

El núcleo Arduino-ESP32 levanta FreeRTOS en el arranque: app_main() crea la tarea loopTask (prioridad 1, núcleo 1) que ejecuta tu setup() y luego repite loop() con yield(). A su alrededor corren las tareas de Wi-Fi, Bluetooth, la pila TCP/IP (LwIP) y el alimentador del watchdog —más de un centenar de tareas activas en un proyecto conectado.

La consecuencia práctica: mientras tu loop() bloquea con delay(5000), el resto del sistema sigue funcionando, pero tu lógica es una sola hebra. Todo lo que debe ser concurrente —leer sensores a 10 Hz, mantener MQTT vivo, refrescar una pantalla, atender un botón— acaba resolviéndose con máquinas de estados enredadas. FreeRTOS resuelve esto con tareas independientes y mecanismos seguros de comunicación.

Regla mental: una tarea por responsabilidad con distinta cadencia (sensor, red, UI), cada una con su prioridad, comunicadas por colas. Nunca una sola megatarea con delays.

Crear tareas: xTaskCreate y afinidad a núcleo

void tareaSensor(void* arg) {
  for (;;) {                 // las tareas NUNCA retornan
    float t = leerSensor();
    xQueueSend(colaTemperatura, &t, 0);
    vTaskDelay(pdMS_TO_TICKS(100));   // 10 Hz, libera la CPU
  }
}

void setup() {
  colaTemperatura = xQueueCreate(10, sizeof(float));
  xTaskCreatePinnedToCore(
    tareaSensor,        // función
    "sensor",           // nombre (visible en el monitor de tareas)
    4096,               // stack en bytes (no en palabras como en FreeRTOS clásico)
    NULL,               // parámetro
    5,                  // prioridad (mayor número = más prioridad)
    NULL,               // handle (útil para borrar/notificar)
    1                   // núcleo 0 o 1; tskNO_AFFINITY para cualquiera
  );
}

void loop() { vTaskDelay(pdMS_TO_TICKS(1000)); }  // loop dormido

Tres detalles que evitan dolores: en el port de ESP32 el stack se indica en bytes (en FreeRTOS de escritorio es en palabras); una tarea es un for(;;) del que nunca se sale —usar return provoca reinicio—; y vTaskDelay() cede la CPU de verdad, a diferencia de delay() que en Arduino-ESP32 también termina cediendo pero es menos explícito con el tick.

Sobre núcleos: Wi-Fi/BT usan mayormente el núcleo 0 y loopTask corre en el 1. Pinea tareas de tiempo crítico (generación de pulsos, control) al núcleo 1 y deja el 0 para la pila de red, o usa tskNO_AFFINITY si no importa.

Prioridades y planificación: quién corre cuándo

FreeRTOS es preemptivo por prioridad con round-robin entre iguales: siempre corre la tarea lista de mayor prioridad; las de prioridad igual se turnan en cada tick (1 kHz por defecto en ESP32). Toda tarea debe bloquearse (delay, cola, semáforo) para existir en paz con las demás; una tarea de prioridad alta que nunca bloquea provoca inanición de todo lo demás y dispara el watchdog.

PrioridadTarea típicaPor qué
1–2Logging, displayPuede esperar sin daño
3–5Sensores, lógica de negocioCadencia decenas de ms
6–9MQTT/Sensores críticosLatencia acotada
10+Control de motor, pulso precisoPreempt sobre la red
>= 18Solo ISR-deferred críticoCasi nunca se necesita

Las tareas del sistema (Wi-Fi, idle) viven en 1 y 23; la idle es especial: alimenta el watchdog de tareas (TWDT) y ejecuta la recuperación de memoria de tareas borradas. Si la idle de un núcleo no corre, el watchdog te lo hará saber con el temido Task watchdog got triggered.

Pasar datos entre tareas: colas

La cola (queue) es el mecanismo rey: FIFO thread-safe de tamaño fijo por elemento. Productor-consumidor clásico:

typedef struct { float temp; uint32_t ms; } Lectura;
QueueHandle_t cola;

void productor(void*) {
  for (;;) {
    Lectura l = { leerSensor(), millis() };
    if (xQueueSend(cola, &l, pdMS_TO_TICKS(100)) != pdPASS)
      contarDescartes();            // cola llena: política explícita
    vTaskDelay(pdMS_TO_TICKS(100));
  }
}

void consumidor(void*) {
  Lectura l;
  for (;;) {
    if (xQueueReceive(cola, &l, portMAX_DELAY) == pdPASS) {
      publicarMQTT(l);
    }
  }
}

Puntos de diseño: dimensiona la cola para absorber ráfagas (no como buffer permanente —si siempre está llena, el productor es más rápido que el consumidor y hay que decidir qué descartar); copia por valor está bien para structs pequeñas, usa punteros con cuidado de propiedad de memoria; y evita compartir variables globales sin protección "porque hasta ahora funcionó".

Semáforos, mutexes y notificaciones

  • Semáforo binario: señal evento→tarea ("llegó datos", "terminó la conversión"). El ISR hace give, la tarea hace take.
  • Mutex (xSemaphoreCreateMutex): proteger acceso exclusivo a un recurso compartido —I2C, un JSON, la UART— con prioridad heredada que mitiga inversión de prioridades. Tómalo, úsalo, suéltalo en el mismo scope; nunca lo entregues desde otra tarea ni lo retengas mientras bloqueas.
  • Notificaciones de tarea (ulTaskNotifyTake / vTaskNotifyGiveFromISR): más livianas que un semáforo (sin objeto kernel), ideales para ISR→tarea. Si solo necesitas despertar, úsalas.
  • Grupos de eventos y streams/buffers: para banderas múltiples o streaming de bytes (audio, GPS) con menor overhead que copiar por cola.

Regla de oro del firmware ordenado: los ISR no procesan, avisan. En la interrupción lees el registro, haces give/notify y sales; el trabajo pesado ocurre en una tarea, con el sistema intacto.

Interrupciones y FromISR

Toda API llamada desde un ISR debe tener sufijo FromISR y ser consciente del contexto:

volatile bool flagDato = false;

void IRAM_ATTR isrEncoder() {
  // mínima lógica: solo registrar y notificar
  BaseType_t mayorPrioridadDespierta = pdFALSE;
  vTaskNotifyGiveFromISR(handleControl, &mayorPrioridadDespierta);
  if (mayorPrioridadDespierta == pdTRUE) portYIELD_FROM_ISR();
}

void tareaControl(void*) {
  for (;;) {
    ulTaskNotifyTake(pdTRUE, portMAX_DELAY);   // consume la notificación
    procesarEncoder();
  }
}

Marca el handler con IRAM_ATTR (ejecuta desde RAM, no de flash que puede estar ocupada en escritura), no uses Serial, delay ni malloc dentro del ISR, y declara compartidas con el ISR como volatile. El portYIELD_FROM_ISR opcional cambia de contexto al salir si despertaste algo urgente —reduce la latencia percibida.

Watchdog, stack y depuración de cuelgues

Las tres averías clásicas y su diagnóstico:

  • Reinicio cíclico con "Guru Meditation Error": casi siempre corrupción por stack de tarea pequeño. Sube el stack (4096–8192 para tareas con Serial/JSON/TLS) y usa uxTaskGetStackHighWaterMark(handle) para dimensionar con fundamento.
  • "Task watchdog got triggered": una tarea de alta prioridad nunca bloquea, o bloqueaste la idle (loop con while apretado sin delay). Solución: bloquea o divide el trabajo; si la espera activa es inevitable y justificada, documenta por qué.
  • Datos corruptos compartidos: variable global tocada desde dos tareas sin mutex o sin atomic. Busca primero el patrón "funciona con prints, falla sin prints": es la firma de una carrera.

Herramientas del propio sistema: uxTaskGetSystemState() y vTaskList() para ver tareas, estados y stack libre; el monitor de excepciones con backtrace decodificado con addr2line; y el Core Debug Level en el IDE para subir la verbosidad sin reescribir logs.

Patrón completo: sensor + comunicación + actuador

Arquitectura que resuelve el 80 % de los proyectos IoT sin llegar a algo inmanejable:

  1. tareaSensor (prio 4, core 1): lee a cadencia fija, publica Lectura por cola.
  2. tareaRed (prio 3, core 0): mantiene Wi-Fi/MQTT, consume la cola, reconecta con backoff.
  3. tareaActuador (prio 6, core 1): recibe órdenes por otra cola, aplica con rampas, nunca bloquea más de unos ms.
  4. loop() dormido (o borrado): queda como supervisor opcional con reinicio por comando.

Cada cola define la política de saturación (descartar lo más viejo con xQueueOverwrite en colas de longitud 1, o contar descartes), y cada tarea tiene su high-water-mark verificado antes de cerrar el firmware. Con este esqueleto, añadir una pantalla OLED o un botón no desestabiliza lo que ya funciona —que es, al final, el punto entero de la multitarea real.

Preguntas frecuentes

¿FreeRTOS viene incluido en Arduino IDE para ESP32?

Sí. El núcleo Arduino-ESP32 corre sobre FreeRTOS: loop() es una tarea más. Solo hace falta incluir FreeRTOS.h para usar colas y semáforos; xTaskCreate ya está disponible.

¿Cómo elijo el tamaño de stack de una tarea?

Empieza en 4096 bytes y mide con uxTaskGetStackHighWaterMark(handle); deja un 30 % de holgura sobre el máximo observado. Tareas con TLS, JSON o Serial suelen necesitar 8192 o más.

¿Cuándo uso un mutex y cuándo una cola?

Mutex para proteger un recurso compartido (bus I2C, struct de configuración); cola para transferir datos o eventos entre tareas con su propia cadencia. Si te encuentras sondeando una bandera global, probablemente querías una cola.

¿Por qué mi ESP32 se reinicia con Guru Meditation Error?

La causa más común es stack insuficiente en una tarea (corrupción de memoria). Aumenta el stack, verifica con el high-water mark y decodifica el backtrace con addr2line para encontrar la tarea culpable.
